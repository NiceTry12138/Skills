# 源码深度阅读与框架梳理 SKILL

## 触发场景

当用户的请求涉及以下任一目标时，自动启用本 SKILL：

- 阅读 / 学习 / 理解 / 分析 函数、类、模块、项目的源码
- 梳理代码的框架结构、分层设计、调用关系
- 输出源码笔记、架构文档、时序流程

## 输出哲学（写给模型自己看）

写出来的笔记应该让**新人能同时做到两件事**：

1. **快速建立全貌**：30 秒内知道这个模块在系统中是什么位置、上下游是谁、每帧在干什么
2. **快速动手维护**：找得到核心数据结构的字段表、关键算法的执行步骤、未使用代码的清单

如果产出的文档只满足其中一个，就是不合格的。

## 核心工作流

### 第 1 步：确定阅读范围与对话 ID

1. 明确用户要分析的目标：函数 / 类 / 模块 / 整个项目
2. 获取当前 conversation_id（若无法获取，使用当前时间戳 `YYYYMMDD_HHMMSS` 代替）
3. 在项目根目录创建工作目录：
   ```
   ThroughtWork/throught_{对话id}/
   ThroughtWork/throught_{对话id}/Image/
   ```
4. 创建主笔记文件：`ThroughtWork/throught_{对话id}/through_{对话id}.md`

### 第 2 步：使用情况预检（关键，不能跳过）

对于范围内的每一个函数 / 类：

1. **先全局搜索其引用**（使用 grep / ripgrep），判断是否有实际调用方
2. 如果**没有任何引用** → 收集到"未使用清单"，**不再深入阅读其实现**
3. 如果**有引用** → 进入第 3 步详细阅读

> 这一步必须在深入之前完成，避免阅读死代码浪费时间。

### 第 3 步：逐项精读源码（严禁猜测）

针对每一个**确实被使用**的函数 / 类，**必须打开实际代码逐行阅读**，禁止依赖以下任何线索做推断：

- ❌ 不允许仅凭函数名 / 类名 / 属性名推断作用
- ❌ 不允许仅凭注释 / docstring 推断作用（注释可能过时或错误）
- ❌ 不允许仅凭文件名 / 目录名推断模块职责

阅读代码后，记录以下内容：

| 字段 | 说明 |
|------|------|
| 名称 | 函数 / 类全限定名 |
| 位置 | 文件路径 + 行号 |
| 实际作用 | **基于代码逻辑**得出的真实功能 |
| 实现原理 | 关键步骤、关键数据结构、关键分支 |
| 调用方 | 谁在调用它 |
| 依赖项 | 它调用了谁 |
| 复杂度标记 | 是否含复杂计算 |

### 第 4 步：核心数据结构字段表（强制）

对每一个**核心数据结构**（结构体 / 类的成员变量、关键 Map/Array 容器），必须产出**字段表**。这是"API 文档"，不是可选项。

**判定"核心"的标准**（满足任一即必须列出）：
- 被 ≥ 2 个模块读写
- 是模块对外暴露的状态载体
- 是 Tick / 主循环中频繁访问的数据
- 包含状态机枚举字段（如 ActionMode / FadeType）

**字段表模板**：

```markdown
#### FXxxData 字段表

| 字段 | 类型 | 作用 | 备注 |
|------|------|------|------|
| `ID` | int32 | NPC 唯一标识 | 主键 |
| `State` | EXxxState | 当前状态机状态 | 枚举值见 §X.Y |
| ... | ... | ... | ... |
```

对**关键枚举**也要单独列出含义，特别是带优先级/顺序语义的枚举：

```markdown
**EXxxFadeType 枚举**（值越大优先级越高）：
- `None(0)` < `FadeOut(1)` < `FadeIn(2)` < `CollisionFade(3)`
```

### 第 5 步：复杂计算的深度解析（强制四要素）

当函数涉及以下情况之一时，**必须单列一节深入说明**：

- 数学 / 几何 / 数值计算
- 算法（排序、搜索、图、DP、贪心、加权分配等）
- 状态机 / 协议解析
- 并发 / 锁 / 调度逻辑
- 加密 / 哈希 / 编解码
- 多阶段流水线（如分帧处理、异步加载链）

**强制四要素**（缺一不可）：

1. **算法原理**：使用了什么思想 / 公式 / 定理
2. **Phase 拆解 或 计算步骤**：多阶段算法必须分 Phase 描述，单阶段算法分步骤
3. **数值走查示例**：**代入具体数字走一遍**，不能只给公式
4. **时间 / 空间复杂度** + **边界条件**

**反面示例（禁止）**：
> 透明度继承公式：`ElapsedTime_new = (CurrentOpacity - StartOpacity) / (TargetOpacity - StartOpacity) × TotalTime`

**正面示例（要求达到）**：
> 透明度继承公式：`ElapsedTime_new = (CurrentOpacity - StartOpacity) / (TargetOpacity - StartOpacity) × TotalTime`
> 
> **数值走查**：FadeOut（1.0→0.0，2 秒）执行到 0.5 时被 CollisionFade（1.0→0.5，1 秒）打断，继承当前透明度 0.5。
> - 起始=1.0，目标=0.5
> - 进度 = (0.5 - 1.0) / (0.5 - 1.0) = 100% × 但实际仅完成 50%
> - 新 ElapsedTime = 50% × 1 秒 = 0.5 秒
> - 结果：透明度无跳变，从 0.5 平滑过渡到 0.5（CollisionFade 目标）

### 第 6 步：分层与"模块在系统中的位置"

**分层必须包含至少 4 层，且至少有以下两类边界层**：

1. **外部接入层（上游）**：谁调用本模块？列出所有外部入口（Lua 接口、事件总线、其他系统的回调注册等）
2. **业务/总控/数据层（内部）**：模块的内部分层
3. **底层依赖层（下游）**：本模块依赖的底层服务（渲染、网络、IO、空间索引等）

**禁止**只写"目录树式分层"——分层必须体现**调用方向**和**与外部世界的边界**。

**模板**：

```markdown
## 2. 框架分层结构

![框架结构](./Image/architecture.svg)

### 2.1 第一层：外部接入层（上游调用方）
- **XXX 系统**：通过 ... 调用本模块的 ...
- **YYY 事件总线**：监听 ... 事件触发 ...

### 2.2 第二层：总控层
- **UXxxManager**：生命周期、Tick 调度、对外接口

### 2.3 第三层：业务子系统层
- **子系统 A**：职责...
- **子系统 B**：职责...

### 2.4 第四层：数据/配置层
- ...

### 2.5 第五层：底层渲染/服务层（下游依赖）
- **ZZZ 渲染系统**：实际执行 ...
- **空间索引 Octree**：提供 ...
```

### 第 7 步：Tick / 主循环调度（强制画分支）

如果模块包含 Tick / 主循环 / 事件循环，**必须画出调度顺序，且包含所有关键分支判断**。

**禁止**只画线性顺序；**必须**画出：
- 状态分支（如 `if bIsPaused`、`if bWaitingForAsset`）
- 早退分支（`return` 条件）
- 子分支差异（如 `bPauseKeepShow` vs 完全暂停）

**模板**：

```
XxxManager::Tick(DeltaTime)
  ├─ TickAllTimers
  ├─ TickAssetLoading
  ├─ [bIsPaused 检查]
  │   ├─ bPauseKeepShow → 只 Tick ShowManager
  │   └─ 完全暂停 → TickDebug 并 return
  ├─ [等待资产就绪]
  │   └─ 未就绪 → return
  ├─ DataManager.Tick
  └─ ShowManager.Tick
```

### 第 8 步：绘制 SVG 图（中文不乱码）

在 `ThroughtWork/throught_{对话id}/Image/` 目录下生成**至少 3 张** SVG 图：

1. **architecture.svg** —— 框架分层图（**必须含上游/下游边界**）
2. **call-graph.svg** —— 关键调用关系图（用箭头标方向）
3. **sequence.svg** —— 核心流程时序图（**必须用泳道区分角色，含分支/循环**）

如果模块有多个核心流程，额外生成 `sequence-{流程名}.svg`。

**SVG 中文不乱码的强制要求**：

```xml
<svg xmlns="http://www.w3.org/2000/svg" ...>
  <style>
    text {
      font-family: "PingFang SC", "Microsoft YaHei", "Noto Sans CJK SC", "SimHei", sans-serif;
    }
  </style>
  <!-- 所有 text 元素直接写中文，不要使用 &#xxxx; 实体 -->
  <text x="100" y="50">业务逻辑层</text>
</svg>
```

要点：
- 文件**直接以 UTF-8 编码保存**
- 字体声明涵盖 macOS / Windows / Linux 常见中文字体
- 不使用 HTML 实体转义中文，直接写汉字
- 避免使用某些渲染器不支持的 `<foreignObject>` 包裹中文

### 第 9 步：功能清单（工程师视角，非产品视角）

如果模块对外提供较多功能（≥10 项），**必须**输出功能清单表。

**风格要求**（重要）：
- ✅ **工程师视角**：说明用了什么数据结构、什么算法、关键阈值
- ❌ **产品视角**：不要只写"NPC 跳跃闪避，支持 4 方向"

**对比示例**：

| 风格 | 示例 |
|------|------|
| ❌ 产品视角（禁止） | "玩家接近时 NPC 跳跃闪避，支持 4 方向" |
| ✅ 工程师视角（要求） | "AABB 检测玩家与 NPC 碰撞，计算 4 方向闪避终点（UCurveFloat 驱动位移），骑马时切换 HorseJumpDodgeRadius" |

**模板**：

```markdown
| # | 功能 | 实现位置 | 实现方式 |
|---|------|---------|----------|
| 1 | XXX | ModuleA::FuncB | 使用 ... 数据结构，... 算法，关键参数 ... |
```

### 第 10 步：标注不确定项

凡是阅读后仍**无法 100% 确定**的部分，**必须显式声明**，禁止伪装成确定结论。使用如下格式：

```markdown
> ⚠️ **不确定**：函数 `foo()` 中第 42 行的位运算用途未能完全确定。
> 推测作用：可能用于位标志压缩存储 X 状态。
> 推测依据：调用方 `bar()` 似乎以位掩码方式读取返回值。
> 仍需验证：缺少 X 状态的定义文件。
```

### 第 11 步：未使用代码独立成节（强制）

**必须单独成节**输出未使用代码清单，禁止只在函数清单里散落标记。

```markdown
## X. 未使用代码清单

| 名称 | 位置 | 类型 | 备注 |
|------|------|------|------|
| `OldFooClass` | `src/x.h:50` | 类 | 完整定义，无引用，推测被 NewFooClass 替代 |
| `helper_y()` | `src/a.py:88` | 函数 | 注释代码块中 |
```
